Method

What is captured, how the drift rule is defined, and why the alarm lives outside the capture job.

What the capture stores, exactly

One JSON line per source per run: run id, trigger, source id, requested and final URL, publisher, tier, fetch start and end in UTC, HTTP status, content type, byte count, SHA-256 of the body, the marker string it must contain and whether it did, the count of <table> and <tr> tags, the previous successful hash, and a delta label of first/unchanged/changed/failed. Raw bodies go to a 90-day workflow artifact, not to git. No player, injury or depth value is stored anywhere in it.

Structural signature

The pair (table-tag count, row-tag count) recorded at capture time. Two captures with the same signature may still differ in content -- a club can rename a player without adding a row -- so the signature is a floor on change, not a ceiling. It is used here for one purpose: deciding whether a byte change was worth reporting.

Band pinning

For each source, the median of its row-tag counts across runs, plus or minus 15%, asserted only once 3 runs exist. A source whose median is 0 is labelled no-structure rather than 'stable at zero': a page that has never yielded a table is a known gap, not a steady state.

Robust outlier test

|count - median| / (1.4826 x MAD) > 3.0, with MAD the median absolute deviation. Median and MAD are used instead of mean and standard deviation because the broken run must not be allowed to move the baseline it is being compared against: with four observations, one 28-row run inside a mean-and-sigma rule absorbs itself and hides the break. When MAD is 0 the band is degenerate and any movement is reported as unbounded surprise rather than divided by zero.

Why the alarm is not inside capture.yml

That workflow and capture/check.py belong to the session that built them. Editing them here would be a scope violation, and silently replacing another session's gate with mine would be worse than adding one. So the rule ships as delta_ledger/check_drift.py with its own workflow, and the board carries the request to fold it into the capture job.

Freshness

Age is not published on these pages: a page that reads the clock cannot be rebuilt byte-identically, and a stale 'fresh' claim is exactly the failure this repository keeps flagging. check_drift.py --ci computes age inside the scheduled job against a 30-hour limit. The limit is 30h because the observed run gaps are 9.96h to 23.44h: Actions schedule times are advisory, so an alarm written against the cron line would fire on ordinary days and stop being believed.

Tiers

official-league (nfl.com), official-club (a club site), dataset (a file in this repository), internal (a computation over those). Nothing here is tier official except the URLs the capture is configured to fetch; the values on these pages are about our own fetches.

Limits of this session

The sandbox reaches github.com, npmjs.org and pypi.org only. No official page was fetched here to confirm a row count or a designation: the numbers are read back from the manifest the Actions runner wrote, and the capture's own claim that a marker string was found is the capture's, not this session's.
