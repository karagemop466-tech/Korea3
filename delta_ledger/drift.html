This is the whole 'surprise, not level' story that the data currently supports: four timestamped reads of the report page, the change between them, and the honest statement that a *player's* designation delta needs parsed values, which the capture does not store and this repository must not publish before the terms decision.

Where this is enforced. python3 delta_ledger/check_drift.py exits non-zero on these events, and --ci adds the age of the newest capture against a 30-hour limit. It is run by its own workflow rather than by capture.yml, because that file belongs to another session; the request to fold the same rule into the capture job is logged on the board. The rule lives in one function (drift.py) shared by the page and the alarm, so the published count and the alarm count cannot diverge.
