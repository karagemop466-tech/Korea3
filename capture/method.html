Method

Exactly what the capture does, and what it does not.

Schedule

  • Daily at 16:20 UTC, and at 01:20 UTC on Thursday, Friday and Saturday (UTC), which is the Wednesday, Thursday and Friday evening in US Pacific time. The cadence is this repository's choice. It is not an NFL rule until an NFL-published policy page is opened and cited (see Flagged for Review, C-02).
  • Manual runs are possible from the Actions tab (workflow_dispatch). Pull requests run only the offline checks; they do not fetch anything.

What is recorded, per source, per run

  • fetch_start_utc / fetch_end_utc: the UTC clock read before and after the request.
  • http_status, final_url, content_type, bytes: what the server returned, after redirects.
  • sha256: SHA-256 of the exact response body. This is the immutable fingerprint.
  • marker_found: whether the required text (for example Practice Status for the injury report, depth for a club depth page) appears in the body. A missing marker is a failure, because it means the page changed shape or was replaced.
  • table_tags, row_tags: counts of <table and <tr tags, shown for structure only. They are not a parsed value.
  • previous_sha256 and delta: the hash of the last successful capture of the same source, and whether this capture is first, unchanged, changed or failed. If a source failed in between, "changed" compares against the last success, so the gap is not hidden.
  • result and reason: ok, or fail with every reason listed.

Failure rules (fail loudly)

  • Any non-200 status, any network error, any body smaller than 2,000 bytes, or any missing marker is a fail row.
  • The scheduled job runs capture/check.py --strict-run after the manifest is committed. A failed run turns the job red, which is the alarm. GitHub notifies the repository's workflow actors of failed scheduled runs.

Storage: what is durable and what is not

  • Durable (in git): capture/data/manifest.jsonl, append-only. It holds the hashes, times, statuses and deltas, and nothing else.
  • Not durable (workflow artifact, 90 days): the raw response bodies. They are too large for git and the brief says to keep large data out of git. A durable off-repository store for raw bodies is an owner decision and is recorded as C-01 on Flagged for Review. Until it is made, a body older than 90 days can be checked only against its recorded hash, not re-read.
  • The hash proves a body was the same bytes at capture time. It does not prove the page is correct, and it does not say anything about who will play.

What this page does not do

  • It parses no injury, designation, depth or player value. Parsing the 32 depth tables and the injury rows into publishable values is a separate task with its own verification (see the depth lab).
  • It does not infer a starter, a replacement or a play probability from a delta.
Every value on this site is a hash, a clock time, a status code, a byte count or a delta between two captures. No injury, depth or player value is published here. Built from capture/data/manifest.jsonl by capture/build.py.
