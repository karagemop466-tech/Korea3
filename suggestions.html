Suggestions — choose a path before implementing

Twelve improvements, each written so it can be accepted or rejected on its own. Nothing here has been implemented as a change to another session's work. The decision column is deliberately empty so the path is chosen here, before any code is written.

S01P1Data integrity Separate the two strategy ID spaces before anything else is joined`data/derived/bets.csv` (line_lab build, IDs S1..S11, 16,439 bets) and `data/derived/gates_results.csv` (pipeline build, IDs S01..S18) both use S-numbered strategy IDs for different rules. `S10` means 'Rest edge of 4+ days to the away team' in one build and something else in the other, so any join on ID silently mixes the two.Prefix every strategy ID with its build (LL- and PL-), add a `build` column to both ledgers, and make the hub builder refuse to join two ledgers unless the namespaces differ. Low (one afternoon)Removes a whole class of wrong-number defects before more data arrives.Breaks any downstream file that hard-codes S01..S18; must be done with a checked migration. Adopt the namespacing now, or freeze both ledgers and never join them?
S02P1Method Record a pre-registration commit hash for every strategyRules can be added or edited after their result is known. Nothing in the build prevents it, and the multiple-comparison correction assumes advance registration.Store the commit hash that introduced each rule, show it on the strategy page, and fail the build if a rule has no registration commit older than its test output. LowMakes the statistical claim honest and auditable.Some historical rules predate the repository; they must be marked 'unregistered' rather than back-filled. Registrations from now on only, or re-register the historical rules and re-test?
S03P1Availability Ship the availability view as an officially-sourced layer, with depth left blankThe brief asks for backup-deficiency analysis, but no official depth chart could be reached, so any string-level number would be invented.Publish exactly what is official: game status, practice status, roster status and reserve moves, aggregated per club and per unit with declared weights. Keep a clearly separated 'depth: not available' column. Medium (this session built the pilot)Delivers the usable half of the brief without fabricating the other half.A reader may mistake the availability index for a depth measure; the labelling must stay blunt. Is the official-layer-only version acceptable as v1, or is a licensed depth feed required first?
S04P2Modelling Pre-register the injury hypothesis before acquiring any historical injury dataThe obvious next step is to test whether injury news beats the closing line. Done in the wrong order it will produce a false edge, exactly as the eighteen earlier rules did: none passed, and the best raw result did not survive multiplicity control.Write the rule, the sample, the pass bar and the kill criterion first; commit them; only then obtain data. Test one hypothesis, not a family. MediumThe only way the result will mean anything.The pre-registered rule may simply fail, which is the expected outcome and still valuable. Fund the data acquisition now, or wait until a single hypothesis is agreed?
S05P2Governance Keep this decision register as a standing, dated pageQuestions, answers and gaps are scattered across six executive summaries written by six sessions.Maintain one register with an owner, a status and a source per row. Add a 'what changed since the last review' section. LowA reviewer can see what is decided and what is still open in one place.Becomes stale if it is not updated with each snapshot. Adopt this page as the canonical register, or keep per-session summaries?
S06P2Governance Decide the reward scheme explicitly, or remove the word 'reward'The brief asks for rewards for top strategies. No pool, sponsor, currency, payout rule or jurisdiction exists, and a reward promise can create legal obligations.Choose one: (a) funded pool with published terms and an eligibility rule, (b) reputation-only leaderboard with no money, (c) drop the competition framing. Low to decide, high to operateRemoves an unanswerable question from the critical path.Option (a) needs legal review before any announcement. Which of (a), (b) or (c)?
S07P2Leaderboard Replace the single ROI ranking with a three-axis boardA single ROI column ranks the luckiest rule first. The repository computes a week-block bootstrap interval, a permutation percentile and a shrunk ROI, but they sit on different pages from the ranking, and the raw-ROI leader is the rule whose data source is unverified.One table with ROI, shrunk ROI, permutation percentile, sample size and required sample, sortable, with an explicit tiebreak rule. LowMakes the competition honest and much harder to misread.More columns is more to read; the default sort must be stated. Default sort on shrunk ROI, or on the permutation percentile?
S08P2Availability Add a weekly refresh with a recorded HTTP status per sourceThe site is a snapshot. Injury pages change hourly and can disappear.A small job that re-checks each official URL, records the status and timestamp, and flags any source that stops resolving. It must not fail the site build when an external site is down. LowTurns 'verified on a date' into a maintained claim.A flaky external site could spam flags; the job must distinguish 'source down' from 'repo broken'. Weekly, or before every game day?
S09P3Modelling Measure player-level pair correlations once a prop-line source existsThe correlation work covers only team-level markets. Prop combinations are documented by mechanism but not measured, because no prop-line archive exists.Acquire a prop-line archive with timestamps, then measure the same phi statistic on the pairs already listed, and compare against each operator's same-game-parlay repricing. HighTurns the prop framework from a hypothesis list into evidence.Operators reprice SGPs, so a measured correlation may not be a measured edge. Is a licensed prop feed worth the cost before the team-level question is settled?
S10P3Site Consolidate six overlapping builds behind one canonical dashboardThe repository serves six generations of dashboards from one GitHub Pages root, each with its own numbers and its own executive summary. A reader cannot tell which is current.Keep the others archived and immutable, but make one page the only entry point, with a single change log and a 'superseded' banner on the rest. MediumRemoves the largest source of reader confusion.Other sessions own those directories; consolidation must be done by whoever owns them, not by overwriting. One canonical dashboard, or keep all six live and clearly dated?
S11P3Data Replace the unprovenanced weather columns or drop themThe wind-based rule (S14, 'Wind 15+ mph: unders') ranked first on raw ROI at +8.41%, but its own source field reads 'wind field from the pinned dataset (UNVERIFIED, no source field)'. A top-ranked rule resting on an unprovenanced column is unusable.Either obtain station-level observations with identifiers, or remove weather from the feature set and mark those rules retired. MediumRemoves a tempting false positive.Retiring a rule reduces the apparent size of the strategy library. Fund a weather source, or retire the weather rules?
S12P3Site Add a change log and per-page 'last verified' stampsEvery page in the dashboard carries the same single snapshot date, so a reader cannot tell which claims were re-checked in this session and which were inherited from an earlier one.Per-source verification date rendered next to the source, plus a single change log page. LowMakes the verification claim precise.Requires disciplined updating, or the stamps become noise. Per-source dates, or a single snapshot date?
